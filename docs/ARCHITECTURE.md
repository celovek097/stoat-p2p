# Архитектура Stoat P2P

Этот документ объясняет, как устроен узел и почему он устроен именно так. Формат событий и сетевые кадры
описаны в [PROTOCOL.md](PROTOCOL.md).

## Идея

Оригинальный Stoat — классическое клиент‑серверное приложение: бэкенд (`delta` — REST, `bonfire` — WebSocket,
`autumn` — файлы, MongoDB, Redis) хранит всё, клиенты ему доверяют. Децентрализовать его можно двумя путями:
переписать клиент под новую сеть или сохранить клиент и заменить «центр». Stoat P2P выбирает второе:

* **каждый пользователь запускает узел**, который реализует API Stoat для *своих* клиентов;
* **между узлами** нет доверия и нет главного — только подписанные события и одинаковые правила их обработки.

Так официальный клиент Stoat (веб, а потенциально и десктоп/мобильный, которые умеют указывать свой сервер)
остаётся без изменений, а централизованная часть исчезает.

## Компоненты узла

```
                ┌──────────────────────── StoatNode (src/node.ts) ─────────────────────────┐
 клиент Stoat → │ REST /api (src/api/routes)   Bonfire /events (src/api/events.ts)         │
                │ Autumn /autumn (src/api/web.ts, files.ts)   веб-клиент /   панель /node   │
                │            │ publish()                         ▲ changes                  │
                │            ▼                                   │                          │
                │   World (src/state/world.ts) ── ServerState (DAG + свёртка), сообщения,   │
                │            │  ▲                  ЛС, профили, ожидание зависимостей        │
                │            ▼  │ ingest()                                                  │
                │   EventStore (src/core/store.ts) — журнал events.jsonl                     │
                │            │  ▲                                                           │
                │            ▼  │                                                           │
                │   PeerManager (src/p2p/manager.ts) — пиры, доступ, синхронизация, LAN      │
                └───────────────────────────────────────────────────────────▲──────────────┘
                                                                            │ WebSocket /p2p
                                                                       другие узлы
```

* **EventStore** — журнал «только на добавление» (`events.jsonl`). Журнал и есть база данных: при старте
  состояние восстанавливается из него, его же узлы реплицируют.
* **World** — всё, что узел знает: состояния серверов, сообщения каналов, ЛС и отношения, профили.
  Принимает события из API и от пиров одинаково (`ingest`), держит события, чьи зависимости ещё не пришли,
  и сообщает об изменениях (`change`) — из них получаются события WebSocket для клиентов.
* **API** — REST, WebSocket и файлы в формате Stoat. Локальные вещи (аккаунты, сессии, настройки клиента,
  непрочитанное) хранятся в `accounts.json` и в сеть не уходят.
* **PeerManager** — соединения с другими узлами: рукопожатие, контроль доступа, подписки, сверка, рассылка.

## Жизненный цикл события

1. Пользователь отправляет сообщение в клиенте → `POST /api/channels/:id/messages`.
2. Маршрут проверяет права локально (для понятной ошибки), затем `node.publish()`:
   * добавляет в `deps` текущие «головы» DAG сервера (что автор видел);
   * для ЛС шифрует тело;
   * подписывает событие ключом пользователя; `id = sha256(канонический JSON)`;
   * для событий состояния сервера делает «пробный прогон» свёртки — если событие ничего не изменит
     (нет прав), клиент получит ошибку `MissingPermission` вместо тихо проигнорированного события.
3. `World.ingest()` проверяет подпись и привязку ключа к ID, область (scope), зависимости; сохраняет в журнал,
   применяет, эмитирует `accepted` и `change`.
4. Bonfire превращает `change` в событие Stoat (`Message`) для всех подключённых клиентов, которым канал виден.
5. PeerManager пересылает событие всем пирам, подписанным на этот scope и имеющим к нему доступ.
6. Узел‑получатель повторяет шаг 3 независимо: проверяет подпись, права, применяет — и его клиенты получают
   `Message`.

## Самоудостоверяемые идентификаторы

Клиенты Stoat ожидают ULID (26 символов) и достают из них время создания. Stoat P2P оставляет 48 бит времени,
а 80 «случайных» бит заменяет битами хеша:

| Объект | Как вычисляется |
| --- | --- |
| пользователь | `ULID(время создания, sha256("stoat-p2p/user/" + pubkey))` |
| сервер | `ULID(ts, sha256("stoat-p2p/server/" + pubkey владельца + "/" + nonce))` |
| канал, роль, сообщение, эмодзи | `ULID(ts события, первые 10 байт id события)` |
| канал ЛС | `ULID(max(время двух пользователей), sha256("stoat-p2p/dm/" + a + ":" + b))` |
| код приглашения | 10 символов из id события `invite.create` |
| файл | `sha256` содержимого (hex) |

Любой узел может проверить, что ID пользователя соответствует ключу, а ID объекта — событию, которое его создало.
Выдать себя за другого пользователя — значит найти вторую прообраз‑коллизию на 80 битах.

## Детерминированное состояние сервера

События, меняющие состояние сервера (`server.update`, `channel.create`, `role.update`, `member.join`, `ban.create`…),
образуют DAG через `deps`. Каждый узел:

1. вычисляет глубину события: `depth = 1 + max(depth(deps))`;
2. упорядочивает все события по `(depth, ts, id)` — это топологический порядок, одинаковый везде;
3. сворачивает их по порядку, начиная с пустого состояния, **проверяя права в момент каждого события**
   ([`applyStateEvent`](../src/state/server.ts)). Недопустимое событие хранится, но ничего не меняет.

Если пришло событие, которое по порядку должно стоять не в конце (параллельная ветка), состояние пересчитывается
целиком («re-fold»), а клиенты получают только разницу ([`diffSnapshots`](../src/state/diff.ts)). При массовой
загрузке пересчёт выполняется один раз на пакет.

Права — порт модели Stoat ([`crates/core/permissions`](https://github.com/stoatchat/stoatchat/tree/main/crates/core/permissions)):
владелец имеет всё; иначе `default_permissions` → переопределения ролей по возрастанию приоритета → для канала
переопределения канала; тайм‑аут оставляет только чтение; без `ViewChannel` — ничего. Ранги ролей защищают
старших: модератор не выгонит администратора и не выдаст роль выше своей.

**Сообщения** не участвуют в DAG как «головы», но ссылаются на головы, которые видел автор. Это даёт позицию
в свёртке: сообщение принимается, если автор был участником в этой позиции. Для правок, реакций и удалений
зависимостью является событие исходного сообщения — оно всегда приходит раньше. Правки, реакции и закрепления
разрешают конфликты по правилу «последний по `(ts, id)` выигрывает».

## Контроль доступа между узлами

Узлы не раздают всё всем:

* **Рукопожатие.** Каждая сторона присылает случайный вызов; другая подписывает его ключом узла и ключами всех
  своих пользователей. Так узел доказывает, каких пользователей он «представляет».
* **Сервер** отдаётся пиру, если тот представляет текущего участника или предъявил действующий код приглашения.
  После бана или выхода узел пользователя перестаёт получать обновления.
* **ЛС** отдаются только узлам одного из двух собеседников (и доверенным ими ретрансляторам).
* **Профили** публичны.
* **Ретрансляторы** (`--relay`) не имеют своих пользователей. Узел, подключаясь к ретранслятору, выдаёт ему
  подписанные пользователями **делегирования** (на 7 дней); ретранслятор предъявляет их другим узлам и
  поэтому может хранить и пересылать данные своих пользователей, пока их узлы выключены.

## Синхронизация

* **Интерес.** Узел следит за scope'ами: серверы, где состоят его пользователи; их ЛС; профили знакомых.
  Ретранслятор — за всем, на что подписаны его пиры.
* **Подписка (`sub`)** сообщает пиру интерес. В ответ пир присылает **сводку**: по каждому дню — число событий и
  хеш их id. Отличающиеся дни запрашиваются списком id, недостающие события — пакетами.
* **Рассылка.** Новое событие сразу уходит всем подписанным пирам с доступом; дубликаты отсекаются по id, петли
  невозможны.
* **Зависимости.** Событие, у которого нет родителей, ждёт в очереди, а недостающие родители запрашиваются у того,
  кто прислал событие.
* **Анти‑энтропия.** Раз в 5 минут и при каждом переподключении сверка повторяется.
* **Приглашения.** Узел, не знающий код, спрашивает пиров (`invite?`); ретранслятор пересылает вопрос дальше.
  Узнав сервер, узел подписывается на него, предъявляя код, скачивает состояние и только тогда публикует
  `member.join`.
* **Поиск своих данных.** При подключении узел спрашивает пиров, в каких серверах и ЛС состоят его пользователи
  (`scopes?`). Это нужно при переносе личности на новый узел или после потери данных.
* **Файлы** адресуются хешем и докачиваются с пиров по запросу, с проверкой хеша.
* **Эфемерное.** «Печатает…» и онлайн‑статус идут отдельными кадрами и не сохраняются.
* **Обнаружение.** Явные адреса (`--peer`), обмен адресами между пирами, UDP‑маяк в локальной сети, адреса
  домашних узлов в профилях пользователей (чтобы найти узел собеседника для ЛС).

## Совместимость с клиентом Stoat

Узел реализует те части API, которые использует официальный клиент и SDK `stoat.js`:

* `GET /` — конфигурация: адреса WebSocket и файлов вычисляются из заголовка `Host`, поэтому один и тот же узел
  доступен и как `localhost`, и по адресу в локальной сети;
* аутентификация, сессии, онбординг, пользователи, серверы, каналы, сообщения, роли, права, приглашения,
  баны, эмодзи, настройки, непрочитанное, поиск;
* WebSocket протокол v1: `Authenticated`, `Ready`, `Message`, `MessageUpdate`, `ServerCreate`,
  `ServerMemberJoin`, `ChannelStartTyping`, `UserUpdate`, …;
* Autumn: загрузка `multipart/form-data`, раздача по `/:tag/:id`.

Веб‑клиент собирается из исходников `stoatchat/for-web` с «заглушками» вместо адресов, а узел подставляет
адреса при каждой раздаче. Файлы, загруженные пользователями, отдаются с `Content-Security-Policy: sandbox` и
`nosniff`, а всё, кроме изображений, видео и аудио, — как вложение, чтобы загруженный HTML не мог выполниться
в контексте клиента.

## Ограничения модели

* Свёртка DAG с проверкой прав по позиции — упрощённая альтернатива state resolution в Matrix. Забаненный
  участник может подписать сообщение со старыми зависимостями; такие сообщения скрываются, если их время позже бана
  («soft fail»), но полностью «задним числом» это не решается.
* Сообщения проверяются по правам на момент получения, а не по историческому состоянию; при последующей
  перестройке DAG их видимость не пересчитывается.
* Содержимое серверов видно всем узлам участников и их ретрансляторам. Сквозное шифрование групп
  (например, MLS) — возможное развитие.
* Транспорт между узлами — WebSocket; шифрование канала обеспечивает TLS (`wss://`) на reverse proxy.
